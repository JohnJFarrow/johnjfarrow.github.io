UL Unreal Threading

November 24, 2025

This article talks about how threading is implemented in Unreal Engine and how to use threading from C++.

The Parallel Stacks Window​

The parallel stacks window in Visual Studio shows you the current thread and all other threads, with the Unreal thread names like "GameThread" and "RenderThread" giving a clear indication which thread you are on.

Looking at this code:

if (!CreateCommands.IsEmpty())
{
	// Must enqueue RT commands to ensure SetTransform & CreateRenderThreadResources are executed in-order.
	ENQUEUE_RENDER_COMMAND(AddPrimitiveCommand)(
		[this, CreateCommands = MoveTemp(CreateCommands)](FRHICommandListBase& RHICmdList)
	{
		for (const FCreateCommand& Command : CreateCommands)
		{
			FScopeCycleCounter Context(Command.PrimitiveSceneProxy->GetStatId());
			Command.PrimitiveSceneProxy->SetTransform(RHICmdList, Command.RenderMatrix, Command.WorldBounds, Command.LocalBounds, Command.AttachmentRootPosition);
			Command.PrimitiveSceneProxy->CreateRenderThreadResources(RHICmdList);

			AddPrimitiveSceneInfo_RenderThread(Command.PrimitiveSceneInfo, Command.PreviousTransform);
		}
	});

The Game Thread​

The game thread owns all AActor/UObject state, and may be writing to it at any time.

The Render Thread​

The entire renderer operates in its own thread that is a frame or two behind the game thread

Data Separation - the Unreal Approach​

  • have data in separate structures owned by specific threads so it is clear which thread can change which data
  • have parallel structures on the game thread and rendering threads (see example below) and copy data to and from these structures. Unreal calls the copying process "mirroring".
  • reduce complexity by having each function only called by one specific thread

Data Separation example:​

UPrimitiveComponent (and derived classes) are SceneComponents that contain or generate some sort of geometry, generally to be rendered, or used for collisions. UPrimitiveComponent is created by and owned by the game thread. The render thread never touches the memory of the UPrimitiveComponent. The rendering thread has a class called FPrimitiveSceneProxy (and corresponding derived classes) which act as a proxy for the UPrimitiveComponent. The game thread never accesses the memory of a FPrimitiveSceneProxy once it has been created and registered.

UActorComponent::RegisterComponent() adds a component to the scene and makes it visible to the renderer by calling FPrimitiveSceneProxy::CreateSceneProxy() which creates a FPrimitiveSceneProxy.

The FPrimitiveSceneProxy will have GetDynamicMeshElements() (or overrides) called on it for every pass that is needed if it is visible.

For a mesh this looks like:

UE::Tasks::FTask FDynamicMeshElementContext::LaunchAsyncTask(FDynamicPrimitiveIndexQueue* PrimitiveIndexQueue, UE::Tasks::ETaskPriority TaskPriority)
{
	return Pipe.Launch(UE_SOURCE_LOCATION, [this, PrimitiveIndexQueue]

void FDynamicMeshElementContext::GatherDynamicMeshElementsForPrimitive(FPrimitiveSceneInfo* Primitive, uint8 ViewMask)
{
	SCOPED_NAMED_EVENT(DynamicPrimitive, FColor::Magenta);

	TArray<int32, TInlineAllocator<4>> MeshBatchCountBefore;
	MeshBatchCountBefore.SetNumUninitialized(Views.Num());
	for (int32 ViewIndex = 0; ViewIndex < Views.Num(); ViewIndex++)
	{
		MeshBatchCountBefore[ViewIndex] = MeshCollector.GetMeshBatchCount(ViewIndex);
	}

	MeshCollector.SetPrimitive(Primitive->Proxy, Primitive->DefaultDynamicHitProxyId);

	// If Custom Render Passes aren't in use, there will be only one group, which is the common case.
	if (ViewFamilyGroups.Num() == 1 || Primitive->Proxy->SinglePassGDME())
	{
		Primitive->Proxy->GetDynamicMeshElements(FirstViewFamily.AllViews, FirstViewFamily, ViewMask, MeshCollector);
	}
	else
	{
		for (FViewFamilyGroup& Group : ViewFamilyGroups)
		{
			if (uint8 MaskedViewMask = ViewMask & Group.ViewSubsetMask)
			{
				Primitive->Proxy->GetDynamicMeshElements(FirstViewFamily.AllViews, *Group.Family, MaskedViewMask, MeshCollector);
			}
		}
	}

	for (int32 ViewIndex = 0; ViewIndex < Views.Num(); ViewIndex++)
	{
		FViewInfo& View = *Views[ViewIndex];

		if (ViewMask & (1 << ViewIndex))
		{
			FDynamicPrimitive& DynamicPrimitive = DynamicPrimitives.Emplace_GetRef();
			DynamicPrimitive.PrimitiveIndex = Primitive->GetIndex();
			DynamicPrimitive.ViewIndex = ViewIndex;
			DynamicPrimitive.StartElementIndex = MeshBatchCountBefore[ViewIndex];
			DynamicPrimitive.EndElementIndex = MeshCollector.GetMeshBatchCount(ViewIndex);
		}
	}
}

UPrimitiveComponent::SendRenderTransform_Concurrent() marks the component as dirty:

{

In FScene::BatchAddPrimitivesInternal the bRenderTransformDirty=true results in a FCreateCommand object being queueed for the render thread. This uses the FRenderThreadCommandPipe to pipe commands to the render thread:



	// Must enqueue RT commands to ensure SetTransform & CreateRenderThreadResources are executed in-order.
	ENQUEUE_RENDER_COMMAND(AddPrimitiveCommand)(
		[this, CreateCommands = MoveTemp(CreateCommands)](FRHICommandListBase& RHICmdList)
	{
		for (const FCreateCommand& Command : CreateCommands)
		{
			FScopeCycleCounter Context(Command.PrimitiveSceneProxy->GetStatId());
			Command.PrimitiveSceneProxy->SetTransform(RHICmdList, Command.RenderMatrix, Command.WorldBounds, Command.LocalBounds, Command.AttachmentRootPosition);
			Command.PrimitiveSceneProxy->CreateRenderThreadResources(RHICmdList);

			AddPrimitiveSceneInfo_RenderThread(Command.PrimitiveSceneInfo, Command.PreviousTransform);
		}
	});

In the above code CreateCommands is a list of FCreateCommand objects which are executed on the render thread. This uses the FTaskThreadBase task system to run the commands.

After this the proxy is moved by a call to FPrimitiveSceneProxy::SetTransform(), on the render thread.

If the buffers of a mesh do change, for example the bone positions of an animated mesh, and array of the changes positions is created on the game thread and passed to the rendering thread which is responsible for deleting it.

Multithreaded UObject Destruction​

Taking a skeletal mesh as an example, this is a UObject (USkeletalMesh) so it is owned by the game thread. When it is loaded render resources are created for (say) the vertex and index buffers. These render resources are owned by the render thread but reference memory (the vertex and index buffers) which are part of the UObject. There is only one copy of the data. The UObject cannot be simply destroyed by the game thread because the render thread might still be using the buffers via the render resources.

When garbage collection determines it wants to destroy the mesh, it calls USkeletalMesh::BeginDestroy(). This calls ReleaseResources():

void USkeletalMesh::ReleaseResources()
{
	FSkeletalMeshRenderData* SkelMeshRenderData = GetResourceForRendering();
	if (SkelMeshRenderData && SkelMeshRenderData->IsInitialized())
	{
		...

		SkelMeshRenderData->ReleaseResources();

		// insert a fence to signal when these commands completed
		ReleaseResourcesFence.BeginFence();
	}
}

The key thing here is the combination of the SkelMeshRenderData->ReleaseResources() call followed ReleaseResourcesFence.Begin() call.

This ReleaseResourcesFence member variable is an object which is used to test if the mesh is ready for destruction. The Begin() call on the fence has the code shown below.

void FRenderCommandFence::BeginFence(ESyncDepth SyncDepth)
{
	...
	ENQUEUE_RENDER_COMMAND(BeginFence)([PipeEvent = MoveTemp(PipeEvent)](FRHICommandList&) mutable
	{
		PipeEvent.Trigger();
	});
}

What happens is the the ReleaseResources() call and the Begin() call both place commands in the render thread pipe, to release the render resources which reference the mesh buffers and to update the fence.

After BeginDestroy() is called the game thread will call IsReadyForFinishDestroy (potentially more than once) to see if the mesh resources are no longer being used by the render thread. If the render thread has processed the two commands in the pipe, the render resources will have been freed (so the mesh buffers are no longer being used by the render thread) and the ReleaseResourcesFence will be marked as complete. If the render thread has not yet processed the calls, the ReleaseResourcesFence will not be marked as complete and the garbage collection thread will try again later. Only if the ReleaseResourcesFence is marked as complete will IsReadyForFinishDestroy() return true:

bool USkeletalMesh::IsReadyForFinishDestroy()
{
	...

	// see if we have hit the resource flush fence
	return ReleaseResourcesFence.IsFenceComplete();
}

Tasks​

The task system enables you to build and execute graphs of tasks. A task can have task prerequisites, which are tasks which must run before the task is started. Tasks can launch nested tasks. Task events exist for signalling between tasks.

Factorizing​

This Factorize() function gives test threads something to do, and takes long enough that it will show up in Unreal Insights:

namespace
{
	void Factorize(unsigned long long n) {

		TRACE_CPUPROFILER_EVENT_SCOPE(Factorize);

		for (unsigned long long i = 1; i * i <= n; ++i) {
			if (n % i == 0) {
				UE_LOG(LogTemp, Warning, TEXT("A factor of %ld is %ld"), n, i);
			}
		}
	}
}

Launching a task​

This uses the function Launch which takes a location and a callable task body (in this case a lambda):

unsigned long long LargeNumber = 99999993700377;

UE::Tasks::Launch(
	UE_SOURCE_LOCATION,
	[LargeNumber] { 
		UE_LOG(LogTemp, Log, TEXT("Factorizing %ul"), LargeNumber );
		Factorize(LargeNumber);
		UE_LOG(LogTemp, Log, TEXT("Done Factorizing %ul"), LargeNumber);
	}
);

````Launch``` is declared in Engine\Source\Runtime\Core\Public\Tasks\Task.h

The UE_SOURCE_LOCATION macro provides a task debug name, used to identify the task and find it in soure code.

Prerequisite Tasks​

There are two versions of Launch:

// launches a task for asynchronous execution
// @param DebugName - a unique name for task identification in debugger and profiler, is compiled out in test/shipping builds
// @param TaskBody - a functor that will be executed asynchronously
// @param Priority - task priority that affects when the task will be executed
// @param TaskFlags - task config options
// @return a trivially relocatable instance that can be used to wait for task completion or to obtain task execution result
template<typename TaskBodyType>
TTask<TInvokeResult_T<TaskBodyType>> Launch(
	const TCHAR* DebugName,
	TaskBodyType&& TaskBody,
	ETaskPriority Priority = ETaskPriority::Normal,
	EExtendedTaskPriority ExtendedPriority = EExtendedTaskPriority::None,
	ETaskFlags Flags = ETaskFlags::None
)
{
	using FResult = TInvokeResult_T<TaskBodyType>;
	TTask<FResult> Task;
	Task.Launch(DebugName, Forward<TaskBodyType>(TaskBody), Priority, ExtendedPriority, Flags);
	return Task;
}

// launches a task for asynchronous execution, with prerequisites that must be completed before the task is scheduled
// @param DebugName - a unique name for task identification in debugger and profiler, is compiled out in test/shipping builds
// @param TaskBody - a functor that will be executed asynchronously
// @param Prerequisites - tasks or task events that must be completed before the task being launched can be scheduled, accepts any 
// iterable collection (.begin()/.end()), `Tasks::Prerequisites()` helper is recommended to create such collection on the fly
// @param Priority - task priority that affects when the task will be executed
// @param TaskFlags - task config options
// @return a trivially relocatable instance that can be used to wait for task completion or to obtain task execution result
template<typename TaskBodyType, typename PrerequisitesCollectionType>
TTask<TInvokeResult_T<TaskBodyType>> Launch(
	const TCHAR* DebugName,
	TaskBodyType&& TaskBody,
	PrerequisitesCollectionType&& Prerequisites,
	ETaskPriority Priority = ETaskPriority::Normal,
	EExtendedTaskPriority ExtendedPriority = EExtendedTaskPriority::None,
	ETaskFlags Flags = ETaskFlags::None
)

The difference is that the second one takes a PrerequisitesCollectionType, which is a list of tasks which must be completed before this task is started. This list can be constructed using the Tasks::Prerequisites() helper function, taking any number of arguments, for example:

UE::Tasks::Prerequisites(LastMeshTask)
UE::Tasks::Prerequisites( SourceTask, ClipTask )
UE::Tasks::Prerequisites(BaseTask, BaseShapeTask, TargetShapeTask)

The code to create two tasks, and have the first one be a prerequisite of the second one, is like this (UE::Tasks::FTask is a task handle):

unsigned long long LargeNumber = 99999993700377;

UE::Tasks::FTask Task1 = UE::Tasks::Launch(
	UE_SOURCE_LOCATION,
	[LargeNumber] { 
		Factorize(LargeNumber);
	}
);

UE::Tasks::FTask Task2 = UE::Tasks::Launch(
	UE_SOURCE_LOCATION,
	[LargeNumber] { 
		Factorize(LargeNumber);
	},
	UE::Tasks::Prerequisites(Task1)
);

Waiting for task completion​

Use

Task1.Wait();

or with a timeout

bool bCompleted = Task1.Wait( FTimespan::FromMilliseconds(1000));

or for multiple tasks:

TArray< FTask > Handles { Task1, Task2 };
UE::Tasks::Wait(Handles);

Checking if task is completed​

bool bDone = Task.IsCompleted();

This call is non-blocking.

Tasks returning results​

TTask<> is a task handle which stores a result of specified type, for example:

UE::Tasks::TTask<int> Task3 = UE::Tasks::Launch(
	UE_SOURCE_LOCATION,
	[LargeNumber]() -> int { 
		const int SleepTime = 10;
		FPlatformProcess::Sleep(SleepTime);
		return SleepTime;
	}
);

int Result = Task3.GetResult();

The call to GetResult() is blocking, it will halt the thread until the task is completed.

Subtasks or Nested Tasks​

If a task launches another task and wants to wait for the second task to complete this can be done in two ways:

using namespace UE::Tasks;

Launch(
	UE_SOURCE_LOCATION,
	[LargeNumber] {
		FTask SubTask = Launch(UE_SOURCE_LOCATION, [] { FPlatformProcess::Sleep(10); });
		SubTask.Wait();
	}
);

In this case the worker thread executing the outer task is block waiting for the subtask to complete. The subtask runs on another thread and the blocked task cannot be used for anything else during this time.

The better approach is:

Launch(
	UE_SOURCE_LOCATION,
	[LargeNumber] {
		FTask SubTask = Launch(UE_SOURCE_LOCATION, [] { FPlatformProcess::Sleep(10); });
		AddNested( SubTask );
	}
);

When you use AddNested() the subtask is executed on the same thread as the outer task so that thread continues to do something.

FPipe​

FPipe implements a list of tasks executed one after the other, if they have no dependencies, or in an order determined by their dependencies, if they have dependencies.

FPipe is used to wrap a shared resource. The tasks in the pipe are executed one at a time so there is no need for locking.

This is the function PipeStressTest from the Unreal Engine 5.7:

	template<uint32 SpawnerGroupsNum, uint32 SpawnersPerGroupNum>
	void PipeStressTest()
	{
		TArray<FTask> SpawnerGroups;
		SpawnerGroups.Reserve(SpawnerGroupsNum);

		constexpr uint32 TasksNum = SpawnerGroupsNum * SpawnersPerGroupNum;
		TArray<FTask> Spawners;
		Spawners.AddDefaulted(TasksNum);
		TArray<FTask> Tasks;
		Tasks.AddDefaulted(TasksNum);

		std::atomic<bool> bExecuting{ false };
		std::atomic<uint32> TasksExecutedNum{ 0 };

		FPipe Pipe{ UE_SOURCE_LOCATION };

		for (uint32 GroupIndex = 0; GroupIndex != SpawnerGroupsNum; ++GroupIndex)
		{
			SpawnerGroups.Add(Launch(UE_SOURCE_LOCATION,
				[
					Spawners = &Spawners[GroupIndex * SpawnersPerGroupNum],
					Tasks = &Tasks[GroupIndex * SpawnersPerGroupNum],
					&bExecuting,
					&TasksExecutedNum,
					&Pipe
				]
				{
					for (uint32 SpawnerIndex = 0; SpawnerIndex != SpawnersPerGroupNum; ++SpawnerIndex)
					{
						Spawners[SpawnerIndex] = Launch(UE_SOURCE_LOCATION,
							[
								Task = &Tasks[SpawnerIndex],
								&bExecuting,
								&TasksExecutedNum,
								&Pipe
							]
							{
								*Task = Pipe.Launch(UE_SOURCE_LOCATION,

									[&bExecuting, &TasksExecutedNum]
									{
										check(!bExecuting);
										bExecuting = true;
										++TasksExecutedNum;
										bExecuting = false;
									}
								);
							}
						);
					}
				}
				));
		}

		Wait(SpawnerGroups);
		Wait(Spawners);
		Wait(Tasks);

		check(TasksExecutedNum == TasksNum);
		Pipe.WaitUntilEmpty();
	}

This function has a number of task spawner groups each of which contains a number of task spawners.

The first highlighted line launches a task for each group. In that group, the second highlighted line launches a task for each spawner within the group. The thrid highlighted line launches a task in the pipe, and this task does some work on the shared resource, in this case incrementing the ```TasksExecutedNum`` variable. Note that this is not an great example - the TasksExecutedNum variable is an std::atomic type so synchronization of concurrent access is not required.

FRunnable​

FRunnable is the base class for representing a thread. A custom runnable object overrides methods in FRunnable like so:

class FCustomRunnable : public FRunnable
{

	FCustomRunnable()
	{
		Thread = FRunnableThread::Create(this, TEXT("CustomThread"));
	};

	virtual bool Init() override
	{
		return true;
	}

	virtual uint32 Run() override
	{
		while (!bShutdown)
		{
			// do thread stuff;
		}
	};

	virtual void Exit() override
	{
	};

	virtual void Stop() override
	{
		bShutdown = true;
	};

	FRunnableThread* Thread;
	bool bShutdown = false;
};

The Init() method is called on the thread which creates the runnable, the Run() and Exit() methods are called on the new thread ru

AsyncTask​

The AsyncTask global function allows you to specify a callable such as a lambda, and which thread it runs on. This enables you to force code to run on the game thread, for example:

// sends InFunction to be called on the GameThread and waits for the result
template<typename RetType>
RetType CallOnGameThread(TFunction<RetType()> InFunction)
{
	TOptional<RetType> Result;
	TAtomic<bool> bCompleted(false);
	AsyncTask(ENamedThreads::GameThread, [&Result, &bCompleted, &InFunction]
	{
		Result = InFunction();
		bCompleted = true;
	});
	while (!bCompleted);
	return MoveTemp(Result.GetValue());
}

ParallelFor​

This iterates an array on multiple threads and executes a callable passing in the current index. This is used when you have a large number of entries in the array:

ParallelFor(ClothFacade.GetNumRenderVertices(), [&TransferBoneWeights, &TargetBoneToIndex, &ClothFacade](int32 VertexID)
{
	TransferBoneWeights.TransferWeightsToPoint(ClothFacade.GetRenderBoneIndices()[VertexID],
		ClothFacade.GetRenderBoneWeights()[VertexID],
		ClothFacade.GetRenderPosition()[VertexID],
		&TargetBoneToIndex);

}, TransferSettings.bUseParallel ? EParallelForFlags::None : EParallelForFlags::ForceSingleThread);

The argments are (1) the array (2) the lamba, and (3) flags. The flags might in fact disable the parallel execution, as shown in the above example.
