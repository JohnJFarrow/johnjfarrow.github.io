UL Gameplay Ability System - Patterns and Practices

November 11, 2025

This article looks at the Gameplay Ability System, both how it works and how it is used in different projects, and attempts to derive some design patterns and practices which can be reused in new projects.

Project Setup​

To use GAS make a C++ project and enable the Gameplay Abilities and Gameplay Abilities Game Feature Actions plugins:

Edit the projects .Build.cs file and add these items to the PublicDependencyModuleNames list: "GameplayAbilities", "GameplayTags", "GameplayTasks", so it looks something similar to this:

PublicDependencyModuleNames.AddRange(new string[] {
    "Core",
    "CoreUObject",
    "Engine",
    "GameplayAbilities", 
    "GameplayTags", 
    "GameplayTasks",
    "InputCore",
    "EnhancedInput",
    "AIModule",
    "StateTreeModule",
    "GameplayStateTreeModule",
    "UMG",
    "Slate"
});

The Ability System Component​

This provides access to most GAS features.

Epic recommends that to support overriding and extending the functionality of the UAbilitySystemComponent component, create a C++ class which derives from UAbilitySystemComponent and use this instead of the UAbilitySystemComponent, because eventually you will want to override or extend UAbilitySystemComponent.

Epic recommends adding the ability system component (ASC) to the PlayerState, not the player actor. This simplifies holding on to state such as attribute sets when the player dies and their pawn is deleted and respawned, or as they move from one level to another.

The IAbilitySystemInterface Interface​

The object which owns the ASC should implement the IAbilitySystemInterface interface. This is not mandatory but is done for performance reasons. If this interface is implemented, code which needs a pointer to the ASC can use the interface directly. If it is not implemented the child components of the owner object must be searched and each one cast in turn until the ASC is found.

To implement this, in the header add these lines:

#include "AbilitySystemInterface.h"

class SomeClassName : public SomeBaseClass, public IAbilitySystemInterface

...
public:
	UAbilitySystemComponent* GetAbilitySystemComponent() const;

and in the cpp file:

UAbilitySystemComponent* SomeClassName::GetAbilitySystemComponent() const
{
    return YourAbilitySystemComp;
}

Multiple objects can hold references to the same ASC and implement IAbilitySystemInterface to hand out references to that ASC even if they do not own, or did not create, it. In Lyra, the player state (ALyraPlayerState) creates and owns the ASC. The player character (ALyraCharacter) is initialized with a call to HandleChangeInitState(). Inside HandleChangeInitState() it calls this:

ALyraPlayerState* LyraPS = GetPlayerState<ALyraPlayerState>();

to get the player state and from the state gets the ASC can caches it in pointer. The player character implements IAbilitySystemInterface and returns this cached pointer to the ASC from GetAbilitySystemComponent() calls.

OwnerActors and Avatars​

The ASC stores two AActor pointers, the OwnerActor and the AvatarActor. Broadly speaking the OwnerActor is the object which controls the ASC, and the AvatarActor is the object in the world which is controlled.

  • the OwnerActor. This is an actor which:
    • for players, should be the pawn, player controller or player state associated with the player
    • for non-player actors, such as a chest or a bomb, should be the actor which contains the ASC
  • the AvatarActor. This is the thing which represents the ASC in the world. It has a physical location. For example:
    • if the ASC is part of a Pawn, then the AvatarActor is that pawn
    • if the ASC is part of a player state, the AvatarActor will be the pawn of the player corresponding to that player state

In the BeginPlay() method, or the PostInitializeComponents() method, of the actor which contains the ASC, call InitAbilityActorInfo() to set the OwnerActor and AvatarActor:

void AProjectCharacter::BeginPlay()
{
	check(HitmanAbilitySystemComponent);
	HitmanAbilitySystemComponent->InitAbilityActorInfo(this, this);
}

Attribute Sets​

An Attribute Sets is a GAS structure which hold a collection of Attributes. Each attribute is a numeric value representing some value such as character health. Beside containing values, attribute sets support additonal functionality such as network replication, listening for changes to values, and being visible in the GAS debugger.

A single object can have multiple associated attribute sets, for example in Lyra the player has ULyraHealthSet, which holds Health, MaxHealth, Healing and Damage attributes, and ULyraCombatSet, which holds BaseDamage and BaseHealth attributes

Lyra also implements ULyraAttributeSet, a utility class from which ULyraHealthSet and ULyraCombatSet attribute sets are derived. It provides useful functions such as GetWorld() and GetLyraAbilitySystemComponent().

The Lyra class ULyraHealthSet looks like this:

UCLASS(BlueprintType)
class LYRAGAME_API ULyraHealthSet : public ULyraAttributeSet
{
	GENERATED_BODY()

public:

	ULyraHealthSet();

	ATTRIBUTE_ACCESSORS(ULyraHealthSet, Health);
	ATTRIBUTE_ACCESSORS(ULyraHealthSet, MaxHealth);
	ATTRIBUTE_ACCESSORS(ULyraHealthSet, Healing);
	ATTRIBUTE_ACCESSORS(ULyraHealthSet, Damage);

	// Delegate when health changes due to damage/healing, some information may be missing on the client
	mutable FLyraAttributeEvent OnHealthChanged;

	// Delegate when max health changes
	mutable FLyraAttributeEvent OnMaxHealthChanged;

	// Delegate to broadcast when the health attribute reaches zero
	mutable FLyraAttributeEvent OnOutOfHealth;

protected:

	UFUNCTION()
	void OnRep_Health(const FGameplayAttributeData& OldValue);

	UFUNCTION()
	void OnRep_MaxHealth(const FGameplayAttributeData& OldValue);

	virtual bool PreGameplayEffectExecute(FGameplayEffectModCallbackData& Data) override;
	virtual void PostGameplayEffectExecute(const FGameplayEffectModCallbackData& Data) override;

	virtual void PreAttributeBaseChange(const FGameplayAttribute& Attribute, float& NewValue) const override;
	virtual void PreAttributeChange(const FGameplayAttribute& Attribute, float& NewValue) override;
	virtual void PostAttributeChange(const FGameplayAttribute& Attribute, float OldValue, float NewValue) override;

	void ClampAttribute(const FGameplayAttribute& Attribute, float& NewValue) const;

private:

	// The current health attribute.  The health will be capped by the max health attribute.  Health is hidden from modifiers so only executions can modify it.
	UPROPERTY(BlueprintReadOnly, ReplicatedUsing = OnRep_Health, Category = "Lyra|Health", Meta = (HideFromModifiers, AllowPrivateAccess = true))
	FGameplayAttributeData Health;

	// The current max health attribute.  Max health is an attribute since gameplay effects can modify it.
	UPROPERTY(BlueprintReadOnly, ReplicatedUsing = OnRep_MaxHealth, Category = "Lyra|Health", Meta = (AllowPrivateAccess = true))
	FGameplayAttributeData MaxHealth;

	// Used to track when the health reaches 0.
	bool bOutOfHealth;

	// Store the health before any changes 
	float MaxHealthBeforeAttributeChange;
	float HealthBeforeAttributeChange;

	// -------------------------------------------------------------------
	//	Meta Attribute (please keep attributes that aren't 'stateful' below 
	// -------------------------------------------------------------------

	// Incoming healing. This is mapped directly to +Health
	UPROPERTY(BlueprintReadOnly, Category="Lyra|Health", Meta=(AllowPrivateAccess=true))
	FGameplayAttributeData Healing;

	// Incoming damage. This is mapped directly to -Health
	UPROPERTY(BlueprintReadOnly, Category="Lyra|Health", Meta=(HideFromModifiers, AllowPrivateAccess=true))
	FGameplayAttributeData Damage;
};

Individual attributes are defined like this:

UPROPERTY(BlueprintReadOnly, 
       ReplicatedUsing = OnRep_Health, 
       Category = "Lyra|Health", 
       Meta = (HideFromModifiers, AllowPrivateAccess = true))
FGameplayAttributeData Health;

Each attribute has an associated set of functions, defined using macros like this:

ATTRIBUTE_ACCESSORS(ULyraHealthSet, Health);

These macros, defined in LyraAttributeSet.h, declare the following functions:

static FGameplayAttribute Get[AttributeName]Attribute();
float Get[AttributeName]() const;
void Set[AttributeName](float NewVal);
void Init[AttributeName](float NewVal);

Attribute Replication​

To replicate an attribute use the ReplicatedUsing parameter:

UPROPERTY(BlueprintReadOnly,    
    ReplicatedUsing = OnRep_Health, 
    Category = "Lyra|Health", 
    Meta = (HideFromModifiers, AllowPrivateAccess = true))
FGameplayAttributeData Health;

The value "OnRep_Health" specifies a method on the attribute set declared like so:

UFUNCTION()
void OnRep_Health(const FGameplayAttributeData& OldValue);

Note that if you forget the UFUNCTION() macro, everything will compile but it won't be called.

In Lyra the OnRep_XXX methods are used to receive a value on the client and then broadcast another value or state changes to listeners. Note that the value received by the OnRep method is the old value of the attribute, the new value is the attribute itself and can be retrieved using Get_[AttributeName];

Prior to Unreal 5.6 attributes which were replicated needed to be coded in the GetLifetimeReplicatedProps() method like so:

void ULyraHealthSet::GetLifetimeReplicatedProps(TArray<FLifetimeProperty>& OutLifetimeProps) const
{
	Super::GetLifetimeReplicatedProps(OutLifetimeProps);

	DOREPLIFETIME_CONDITION_NOTIFY(ULyraHealthSet, Health, COND_None, REPNOTIFY_Always);
	DOREPLIFETIME_CONDITION_NOTIFY(ULyraHealthSet, MaxHealth, COND_None, REPNOTIFY_Always);
}

With 5.6 and after replicated UProperties no longer need to register themselves via DOREPLIFETIME in GetLifetimeReplicatedProps. See 5.6 Release Notes

info

Note that if you look at the declaration of ULyraHealthSet, you do not see a declaration of GetLifetimeReplicatedProps(), but there is an implementation in the cpp file. What happens here is the Unreal Header Tool detects that there are properties with the "ReplicatedUsing" parameter and also that there is no existing declaration of GetLifetimeReplicatedProps(), and generates a declaration for you. This declaration is in the "LyraHealthSet.generated.h" file as part of the GENERATED_BODY macro, so is inserted into the class declaration when the GENERATED_BODY macro is expanded.

If you declare a property with the "ReplicatedUsing" parameter and don't declare or define GetLifetimeReplicatedProps(), the header tool will declare one for you and you will get a linker error like this (because it is declared but not defined):

public: virtual void __cdecl UHealthAttributeSet::GetLifetimeReplicatedProps(class TArray<class FLifetimeProperty,class TSizedDefaultAllocator<32> > &)const " (?GetLifetimeReplicatedProps@UNyetHealthAttributeSet@@UEBAXAEAV?$TArray@VFLifetimeProperty@@V?$TSizedDefaultAllocator@$0CA@@@@@@Z) -Win64-DebugGame.dll : fatal error LNK1120: 1 unresolved externals

Attribute Initialization​

Attributes can be initalized in many ways. The simplest is initialize them in the attribute set constructor as is done in Lyra:

ULyraHealthSet::ULyraHealthSet()
    : Health(100.0f)
    , MaxHealth(100.0f)
{
    bOutOfHealth = false;
    
    MaxHealthBeforeAttributeChange = 0.0f;
    HealthBeforeAttributeChange = 0.0f;
}

The most complex, and the most flexible, way is to initialize attributes from curve tables. Curve tables are assets which can be edited in the Unreal editor, so this approach gives non-programmers the ability so set the initial values of attributes.

To do this override the method BeginPlay() on the actor which owns the ASC and call InitAttributeSetDefaults():

void ANyetCharacter::BeginPlay()
{
	Super::BeginPlay();

	NyetAbilitySystemComponent->InitAbilityActorInfo(this, this);

	if (UAbilitySystemGlobals* Globals = IGameplayAbilitiesModule::Get().GetAbilitySystemGlobals())
	{
		if (FAttributeSetInitter* Initter = Globals->GetAttributeSetInitter())
		{
			Initter->InitAttributeSetDefaults(NyetAbilitySystemComponent, "MainCharacter", 1, true);
		}
	}
}

Don't call Initter->InitAttributeSetDefaults() in PostInitializeComponents(), the world subsystems like UGameplayMessageSubsystem have not be initialized at that point.

A project has a collection of curve tables in the project property Global Attribute Set Defaults Tables. Each of these curve tables has multiple curves each of which matches a single attribute.

Each curve has a name which is split into three parts, such as "MainCharacter.HealthAttributeSet.Health" and the call to InitAttributeSetDefaults() matches the string passed as the second argument to the first part, the ability set name to the second part, and the attribute name to the third part.

Looking at a curve table like this:

The first part "MainCharacter" is compared to the string passed to InitAttributeSetDefaults().

The second part "HealthAttributeSet" is compared to the attribute set name specifed when it is created by the owning actor:

HealthAttributeSet = CreateDefaultSubobject<UNyetHealthAttributeSet>(TEXT("HealthAttributeSet"));

The third part is compared the name of the attribute:

FGameplayAttributeData Health;
info

The tables specified by the property Global Attribute Set Defaults Tables are read once when the editor process is started and cached in memory. If you change the tables without restarting the editor those changes won't be seen by the call to InitAttributeSetDefaults()

info

If no tables are specified by the by the property Global Attribute Set Defaults Tables the call to GetAbilitySystemGlobals()->GetAttributeSetInitter() will return null.

Another way of initializing attribute is to apply a gameplay effect in BeginPlay() which initializeds each attribute. This is discussed later.

Gameplay Effects​

A gameplay effect is a way of changing gameplay attributes and gameplay tags belonging to an actor.

A gameplay effect has a property which determines how it will be applied:

  • instant gameplay effects are applied immediately and the changes they make, such as changing attributes, are permanent
  • duration gameplay effects are added to the actor's list of active effects, and then removed after a certain duration has passed. Duration effects make changes, such as adding tags or changing attributes, which are not permanent, and which are reversed when the effect is removed.
  • a periodic gameplay effect has a duration and a period, and each period the effect is applied again. For example a heal-over-time effect might heal the player 100 units every second for 10 seconds. The changes they make, such as adding tags or changing attributes, are permanent, they are not reversed when the effect is removed. Period effects cannot be predicted.
  • infinite gameplay effects are added to the actor's list of active effects. The changes they make, such as adding tags or changing attributes, remain until the gameplay effect is removed. They do not have a duration, they remain until removed.

UGameplayEffect is a data only class. These are not usually instantiated, instead a GameplayEffectSpec is created which holds a reference to the gameplay effect plus other data such as the level of the effect and the actor which created it.

The method UAbilitySystemComponent::MakeOutgoingSpec() creates a GameplayEffectSpec.

An ASC has a collection of FActiveGameplayEffect called ActiveGameplayEffects.

A simple instant gameplay effect looks like this:

#include "CoreMinimal.h"
#include "GameplayEffect.h"
#include "DamageGameplayEffect.generated.h"

UCLASS()
class UDamageGameplayEffect : public UGameplayEffect
{
	GENERATED_BODY()

public:
	UDamageGameplayEffect();
};
#include "DamageGameplayEffect.h"
#include "NyetHealthAttributeSet.h"
#include "NyetGameplayTags.h"

UDamageGameplayEffect::UDamageGameplayEffect()
{
    DurationPolicy = EGameplayEffectDurationType::Instant;

    FGameplayModifierInfo Modifier;
    Modifier.Attribute = FGameplayAttribute(UNyetHealthAttributeSet::GetHealthAttribute());
    Modifier.ModifierOp = EGameplayModOp::Additive;
    Modifier.ModifierMagnitude = FScalableFloat(-100.0f); 
    Modifiers.Add(Modifier);
}

This effect creates a Modifier which reduces the health attribute of the target by 100.

The class is decorated with a simple UCLASS(). There is no need to declare it a BlueprintType, it is automatically accessible from blueprint. The code to register the type is generated in FileName.generated.h and FileName.gen.cpp.

Clamping Attributes​

An attribute set can limit what a gameplay effect can do to contained attribute values. You can override PreAttributeChange() on the attribute set to check the proposed new value for an attribute, and change that new value if it is not acceptable.

For example if a player has a minimum, maximum and current health the PreAttributeChange() might clamp the current health to be between the minimum and maximum like so:

void UNyetHealthAttributeSet::PreAttributeChange(const FGameplayAttribute& Attribute, float& NewValue)
{
	if (Attribute == GetHealthAttribute())
	{
		NewValue = FMath::Clamp(NewValue, GetMinHealth(), GetMaxHealth());
	}

	Super::PreAttributeChange(Attribute, NewValue);
}

This does introduce complications however. Looking at the attribute initialization curve table we used previously:

What happens now is we attempt to initialize the Health attribute to 500, but the PreAttributeChange() call clamps it to between the current MinHealth and MaxHealth value which are both 0 because we haven't initialized them yet so the Health value is erroneously clamped to 0. To fix this we need to reorder the initial values in the curve table.

Broadcasting Attribute Changes​

Assuming we have created a HUD with widget blueprint and we are using the Gameplay Message Router plugin as all described here, we want to broadcast a message to the HUD whenever the player health value changes.

We need to add a struct which contains the values we will broadcast:

USTRUCT(BlueprintType)
struct FNyetPlayerStats 
{
	GENERATED_BODY()
	UPROPERTY(BlueprintReadonly)
	float Health = 0.0f;
};

We need to add a gameplay tag Broadcast.Player.Stats.

Single Player​

For a single player ae we can use the PostAttributeChange() method on the attribute set to do this:

Add a declaration to the attribute set header file:

public:
virtual void PostAttributeChange(const FGameplayAttribute& Attribute, float OldValue, float NewValue) override;

Add an implementation:

#include "GameFramework/GameplayMessageSubsystem.h"
#include "NyetPlayerStats.h"
#include "NyetGameplayTags.h"

...
void UNyetHealthAttributeSet::PostAttributeChange(const FGameplayAttribute& Attribute, float OldValue, float NewValue)
{
	Super::PostAttributeChange(Attribute, OldValue, NewValue);

	if (Attribute == GetHealthAttribute())
	{
		FNyetPlayerStats Stats;
		Stats.Health = NewValue;

		if (UWorld* World = GetWorld() )
		{
			if (UGameplayMessageSubsystem* Router = UGameInstance::GetSubsystem<UGameplayMessageSubsystem>(World->GetGameInstance()); Router && IsValid(Router))
			{
				Router->BroadcastMessage(GameplayTags::Broadcast_Player_Stats, Stats);
			}
		}
	}
}

This will broadcast the stats structure containing the health attribute whenever it changes and the Gameplay Message Subsystem is running.

Multiplayer​

PostAttributeChange() is only called locally, we need to respond when the attribute value is changed on the server and replicated to the client. When this replication occurs the method named in the UPROPERTY() declaration of the attribute (OnRep_Health in the example below) is called:

UPROPERTY(BlueprintReadOnly, ReplicatedUsing = OnRep_Health, Category = "Lyra|Health", Meta = (HideFromModifiers, AllowPrivateAccess = true))
FGameplayAttributeData Health;

In the OnRep method we get the new value and broadcast it to whoever is listening:

void UNyetHealthAttributeSet::OnRep_Health(const FGameplayAttributeData& OldValue)
{
	GAMEPLAYATTRIBUTE_REPNOTIFY( ThisClass, Health, OldValue );

	FNyetPlayerStats Stats;
	Stats.Health = GetHealth();

	if (UWorld* World = GetWorld())
	{
		if (UGameplayMessageSubsystem* Router = UGameInstance::GetSubsystem<UGameplayMessageSubsystem>(World->GetGameInstance()); Router && IsValid(Router))
		{
			Router->BroadcastMessage(GameplayTags::Broadcast_Player_Stats, Stats);
		}
	}
}

The GAMEPLAYATTRIBUTE_REPNOTIFY is necessary. It invokes GAS’s internal replication callbacks to do things like notify listening blueprints.

This works but has a problem. If we start the game with Number of Players = 2, Net Mode = Play as Client, and we press X to execute the gameplay effect on one of the clients, we can see that the server call to OnRep_Health is replicated to both clients and they both update the UI. The problem is that the OnRep notification is for the client who change the value to let them know their health has changed but on the other client it is letting them know the other client's health has changed.

Each client machine has 2 instances of the actor on it, one is the player (the autonomous proxy), the other is for the second player(the simulated proxy). We only want to update the UI if the health of the autonomous proxy is changed.

This can be fixed by adding a utility function into the projects base attribute set:

AActor* UNyetAttributeSet::GetActorOwner() const
{
    if (const UAbilitySystemComponent* ASC = GetOwningAbilitySystemComponent())
	{
		return ASC->GetOwner();
	}
	return nullptr;
}

and using this function in the OnRepHealth() method to test whether the actor is the autonomous proxy, and only update the UI (i.e. only broadcast the stats update) if that is true.

void UNyetHealthAttributeSet::OnRep_Health(const FGameplayAttributeData& OldValue)
{
	GAMEPLAYATTRIBUTE_REPNOTIFY(ThisClass, Health, OldValue);
	
	if (const AActor* Owner = GetActorOwner())
	{
		const ENetRole Role = Owner->GetLocalRole();
		if (Role == ROLE_AutonomousProxy)
		{
			if (UWorld* World = GetWorld())
			{
				if (UGameplayMessageSubsystem* Router = UGameInstance::GetSubsystem<UGameplayMessageSubsystem>(World->GetGameInstance()); Router && IsValid(Router))
				{
					FNyetPlayerStats Stats{ .Health = GetHealth() };
					Router->BroadcastMessage(GameplayTags::Broadcast_Player_Stats, Stats);
				}
			}
		}
	}
}
